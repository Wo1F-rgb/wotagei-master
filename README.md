# ヲタ芸マスター

動画やインカメを、お手本と8カウントに合わせて比較するWebアプリ。HTML・CSS・JavaScriptと骨格モデルをGitHub Pagesで配信します。ChatGPTへのログイン、自前のアプリサーバー、APIキーは不要です。

## 使い方

1. お手本の動画ファイル、またはYouTube・Twitter/Xの投稿リンクを選びます。
2. 自分の動画ファイルを選ぶか、インカメを起動します。
3. 動画2本の比較は、各動画の「設定 → 拍・BPM」でBPMを設定します。動画ファイルまたは取り込み済みX動画なら、下の「1拍目」で両方の映像を同じ「1」の瞬間に合わせ、「この2点を保存」して「同期再生」を押します。インカメはBPM未設定でも「練習再生」で始められます。
4. 動画ファイルまたは取り込み済みX動画なら「重ねる → 位置 → 動画全体で自動補正」で対象の2人を確認し、「この2人で解析」を押します。BPMと拍の位置を先に合わせてください。インカメや1コマだけの補正も使えます。
5. 次回は「履歴」から保存済みの動画・URLを読み直せます。

## BPMと拍の自動解析

各動画の「設定 → 拍・BPM → 自動解析 → 解析を開始」で、音からBPMと白い拍グリッドをまとめて推定します。約8秒の波形を見ながら「最初・中間・最後」「拍音で再生」で確認し、必要ならBPM、½・×2、「1」の位置を調整して「BPMと拍を使う」を押します。確認前には保存しません。BPMと拍の位置を一緒に、計算に使う精度のまま保存します。「1」「5」は高い拍音です。

音楽上の小節の頭と、踊り始めの「1」は別です。「今の再生位置を『1』にする」は、現在の白線のうち最も近い拍を新しい「1」にします。拍の間隔・手動の位相調整は維持します。曲が変速する場合や検出が安定しない場合は固定グリッドを自動適用しません。

動画ファイルと取り込み済みX動画が対象です。8秒〜10分・160MB以内。別のMP3/M4A/WAVなども選べますが、動画と切り出し位置が異なるためBPMだけを使います。YouTube・Apple Musicの配信音声を直接抽出する機能ではありません。

[Beat This!](https://github.com/CPJKU/beat_this) の小型モデルをブラウザのWorker内で実行します。十分な拍を検出できない場合は、音の立ち上がりと低音の周期を使う補助解析で確認します。全体の拍から外れ値を除いてBPMと位相を推定し、最初の1点に合わせて後半をずらす方式を避けます。再生中のシークや速度の追いかけ補正は追加していません。動画・音声はアップロードしません。初回解析時にモデル約10.6MBとWASM約14MBなどを取得します。

提供された実動画2本でブラウザ解析・確認画面・保存まで検証しました。結果と限界は[検証記録](docs/beat-grid-validation.md)に記載しています。iPhone実機の速度・音の出方は未検証です。

## インカメでライブ練習・録画

インカメの録画は **横16:9（1280×720・最大30fps）** が標準です。「自分の設定 → 動画 → インカメの録画サイズ」で縦9:16も選べます。「比較」では録画と同じ比率の枠に映像を収めます。録画中に端末を回してカメラの幅・高さが入れ替わっても、保存サイズは固定です。映像を横倒しにしたり引き伸ばしたりせず、全体を残して余白を入れます。広く横に撮る場合はiPhoneを横向きにしてください。重ね表示の位置調整・反転・背景処理は録画には入りません。

カメラには横長の画角を要求しますが、ブラウザが実際に返す映像の形は端末や向きによって異なります。iPhone 17の標準カメラの自動回転はAppleが写真向けとして案内している機能で、Safariから同じセンサー領域を選べる保証はありません。[AppleのCenter Stage案内](https://support.apple.com/en-us/111102) / [カメラの画角指定](https://developer.mozilla.org/en-US/docs/Web/API/MediaTrackConstraints/aspectRatio)。録画時だけ[固定サイズのCanvas映像](https://developer.mozilla.org/en-US/docs/Web/API/HTMLCanvasElement/captureStream)を作り、ライブプレビューは元のカメラ映像を直接表示します。

動画ファイル・取り込み済みX動画の曲を含める場合は、録画開始前に約1秒「録画を準備中…」と表示し、音声と映像の入力を準備します。曲とカメラは動き続け、赤い「REC」が出てから録画します。準備中は録画ボタンの「中止」で取り消せます。

横動画の検証：合成カメラの入力を録画中に720×1280 → 960×960 → 1280×720へ変え、保存した1280×720のMP4をデコードして、各場面の四隅の色・向き・余白と音声を確認しました。縦9:16の明示的な選択と保存、同じカメラを維持した繰り返し録画も確認しました。Chromeで縦横4サイズ・比較／重ねるの8状態を確認しています。Safariのセンサー制御・iPhone 17実機の画角や性能を確認した結果ではありません。

インカメは常に自分を映しながら練習するモードです。自分側で「インカメ」を起動し、「比較」または「重ねる」を選びます。動画の操作欄にある「再生」、または下の「練習再生」でお手本の映像と曲を再生します。カメラ側のBPM設定や事前の録画・解析は不要です。カメラはリアルタイムのまま、お手本の映像と音だけを下の×倍率で遅くできます。YouTubeも再生中に速度を変更でき、対応しない倍率は確認して最も近い速度に調整します。お手本を停止してもカメラは映り続けます。

「録画」は再生とは独立しています。曲を流してから押すと、曲を止めたり頭出ししたりせずに自分の映像を録画し始めます。録画中もお手本の再生・停止、速度変更ができ、「終了」で録画だけを終了します。お手本やカメラを止めず、そのまま練習を続けられます。録画終了後は映像内の「録画を保存」から端末に保存できます。カメラ停止・ページを非表示にした場合も録画を終了します。

- **動画ファイル・取り込み済みX動画：** 自分のカメラ映像と、再生したお手本の音を保存します。遅くした音もその速度で入ります。元動画が無音の場合は曲の音は入りません。
- **YouTube・iPhone：** 「録画 → マイクで音を入れて録画」でマイクを許可し、スピーカーで曲を流してください。周囲の声・足音も入ります。イヤホンから流す曲は拾えません。録画中は「REC・マイク」と表示します。通話向けのエコー除去・ノイズ抑制・自動音量調整はOFFを要求し、対応ブラウザでは音声セッションを再生＋録音へ切り替え、終了後に戻します。実際の音量・集音品質は端末や置き方に依存します。
- **YouTube・PCのChrome/Edge：** 「録画 → タブの音で録画」で、このヲタ芸マスターのタブを選び「タブの音声も共有」をオンにします。マイクを使わず、再生中のタブ音声をカメラ映像と一緒に保存します。画面全体・ウィンドウを選んだ場合や、音声共有がない場合は開始せず選び直せます。共有を終了すると録画も終了し、そこまでを保存できます。
- **YouTube・音なし：** 従来どおり自分のカメラ映像だけの録画も選べます。マイクやタブ共有は要求しません。

録画する映像は自分のカメラです。お手本との重ね表示や画面上のボタン、共有した画面の映像は保存しません。タブの音には同じタブで鳴らした拍音なども含みます。録画は端末内で行い、保存前にページを再読み込みすると失われます。録画ボタンを押すまで録画は始まりません。マイクや共有は明示的に選んだときだけ要求し、終了・中止時に停止します。許可待ちを中止した後で許可が返ってきても録画せず、取得した入力を停止します。曲の取り込みには [Web Audioの音声出力ストリーム](https://developer.mozilla.org/en-US/docs/Web/API/MediaStreamAudioDestinationNode/stream)、保存には [MediaRecorder](https://webkit.org/blog/11353/mediarecorder-api/) を使用し、対応する場合はH.264/AACのMP4を優先します。

YouTube IFrame API自体は音声データを返しません。PCのタブ共有はブラウザが利用者の許可に基づいて音を渡す別の仕組みです。Safari iOSは現在 `getDisplayMedia` 非対応なので、GitHub PagesのWebアプリ内から同じ方法で内部音声を取得することはできません。[YouTube IFrame API](https://developers.google.com/youtube/iframe_api_reference)、[Chromeのタブ音声共有](https://developer.chrome.com/docs/web-platform/screen-sharing-controls)、[MDNの互換性データ](https://github.com/mdn/browser-compat-data/blob/main/api/MediaDevices.json)、[マイクのエコー除去](https://developer.mozilla.org/en-US/docs/Web/API/MediaTrackConstraints/echoCancellation)、[AudioSessionの再生＋録音](https://developer.mozilla.org/en-US/docs/Web/API/AudioSession/type)。

検証：Chromeの実カメラAPIにテスト用カメラを接続し、BPM未設定の開始、以前の自分の音・低速設定からの切り替え、0.5・0.75倍での再生と録画、繰り返し録画、録画中の再生停止・再開、カメラの継続を確認しました。保存ファイルをデコードして音声入りを確認し、実際のYouTube埋め込みでも再生中の速度変更と同時録画を確認しました。iPhone相当の縦横4サイズで操作欄の重なりがないことを確認しています。iPhone実機の音声出力・録画確認は未実施です。

YouTube音声の追加検証：テスト用マイクの入力を録音し、終了後の解放、許可拒否、遅れて返る許可の中止、音声入力の終了、無音録画の選択を確認しました。PCのタブ録音は擬似音声入力を無効にし、実際のYouTube埋め込みが再生する音を `getDisplayMedia` から取得してH.264/AACのMP4に保存し、デコードした音声が無音でないことを確認しました。映像源だけは合成カメラ、共有選択には隔離したテスト用Chromeの自動選択フラグを使用しています。公開アプリでは毎回、利用者がブラウザの共有画面で選びます。録画中の0.5・0.75・1倍変更でお手本の停止・シークが起きず、終了時にマイク・共有の全トラックが停止し、カメラはライブを保つことを確認しました。iPhone相当の3サイズで音選択の表示を確認しましたが、iPhone本体のスピーカーからマイクへ回り込む音の品質は未検証です。

## Xの複数動画と自動位置合わせ

1つの投稿に複数の動画があると、お手本の上部に「〈 動画1/2 〉」を表示します。矢印で前後の動画に切り替え、写真は飛ばします。最初・最後で折り返しません。読込中は矢印を止め、「中止」で元の動画を保持できます。取得に失敗した場合も元の映像を残します。

BPM・最初の「1」・反転は動画ごとに保存・復元します。別動画に切り替わった時点で、前の動画の位置・倍率補正を解除します。自分の動画は維持します。各動画へのリンクも履歴に残ります。

Xの動画は端末に取り込んでから解析するため、1コマ／動画全体の骨格補正が使えます。まずBPMと拍を合わせ、**「重ねる → 位置 → 動画全体で自動補正」**を選んでください。動画の中身を解析サーバーへ送信しません。

YouTubeの自動撮影については[方法の比較と実験結果](docs/youtube-frame-research.md)を参照してください。PCのタブ共有とブラウザ自動撮影によるフレーム取得を試作検証しましたが、公開アプリにはまだ組み込んでいません。

## 拍タップと白い拍線

「1拍目」画面では、お手本と自分をそれぞれ1拍単位・0.02秒単位・秒数の直接入力で動かせます。「2拍前から拍音で確認」で両方を同じ拍の位置から再生し、「この2点を保存」で端末に保存します。「1拍目から再生」は、その2点から始めます。動画の先頭が近く2拍分戻れないときは、両方で同じ拍数だけ戻ります。設定時は古いループをOFFにし、切り抜き前の元映像で位置を確認します。

タップ間隔だけでなく、タップした動画の再生時刻からBPMと拍の位置を同時に推定します。最初にタップした拍を「1」として数えますが、その最初の時刻にも固定せず、有効なタップ全体から等間隔の拍線を当てはめます。大きく外れたタップや二重タップの影響を抑え、抜けた拍を推定します。上段の点が実際のタップ、白線と下段の点が補正後の拍です。白い拍線・8カウント・2本の動画の同期に同じBPMと起点を使います。

64回の入力は不要です。2回から暫定推定を始め、有効な結果をこの画面に保持します。「拍音で確認」で聴いてから「保存して戻る」でこの端末に保存します。4〜16回程度が目安です。途中でタップをやめても、停止・画面切替・動画終了でも結果は残ります。再生位置変更や読み込み中断では記録を区切り、違う区間のタップを混ぜません。「再生してやり直す」で新しい記録を始められます。新しい推定が成立するまでは既存のBPM・起点を維持します。

少数のタップではテンポの倍・半分や押し間違いを区別できない場合があります。すべてのタップが一律に遅れる癖はタップだけでは判別できないため、必要なら「拍の位置」か下の矢印か「トラック」で微調整してください。テンポが途中で変わる曲は練習区間ごとに設定してください。

## 画面に触れて位置を合わせる

「重ねる → 位置」を開き、**位置の主役**を「お手本／自分」から選びます。主役は固定し、もう片方だけを操作します。音の主役は下の「曲」で別に選びます。主役を切り替えても、それまでに動かした両方の位置を保持します。

- 画面を1本指でドラッグすると移動、2本指でピンチすると拡大縮小します。指で挟んだ場所を基準に拡縮し、片方の指を離した後もその位置からドラッグできます。
- PCはマウスのドラッグとホイールでも操作できます。操作面にフォーカスすると矢印キーで1%、Shift併用で5%の移動、＋／−で拡縮できます。
- 倍率・位置・濃さ・傾き・遠近のスライダーも使えます。「位置・遠近をリセット」は調整中の相手側だけを戻します。
- YouTubeも手動で移動・拡縮できます。「自分」を位置の主役にするとYouTube側を動かせます。プレイヤーを再生成せず表示の変換だけを変更します。「YouTubeを操作」中は一時的に元の位置・倍率で表示して埋め込みのボタンを操作できます。重ね表示へ戻すと調整を復元します。
- 動画ファイル／取り込み済みXの自動補正も、選択した主役の現在の位置・倍率を固定して、相手を合わせます。

直接操作は位置調整の画面を開いている間だけ有効です。「完了」で確定した見た目のまま練習画面へ戻ります。補正は開いている画面内で保持し、別の動画に変更すると両方をリセットします。再読み込み後はやり直してください。YouTubeの骨格による自動補正は引き続き未対応です。

検証：Chromeでタッチのドラッグ、2本指ピンチ、指を離した後の継続、主役変更、PCホイール、YouTubeのプレイヤー維持、実映像の1コマ／全体の骨格補正を確認しました。スマホ相当の縦横画面も確認していますが、iPhone実機での確認ではありません。

## 動画全体の自動サイズ補正

同期して比較できる区間全体から32組を解析します。選択中の場面も同期区間内なら含め、その相手側はBPMと拍から時刻を計算します。最初に選んだ人物と共通して見える肩・腰の位置と大きさに近い候補だけを使い、観客しか残らない場面や人物が曖昧な場面は除外します。対象を見失った場合は、見えている別人へ自動で切り替えません。大きく移動する動画や人が重なる動画では利用できない場合があります。

人物が映る区間が一部だけでも、1組以上の使える場面から補正します。両方で見える胴体の左右の長さを重み1、肩幅を重み0.5として、可視性で重み付けした長さ比の中央値で倍率を求めます。1.4倍を超えて外れる測定を除き、腰中心75%・足首中心25%で位置を決めます。足首が隠れている場合は腰だけ、腰が隠れている場合は共通する肩や片側の胴体を使います。画面外に推定された関節は除外します。全身・仁王立ちは必須ではありません。

長さを測れない場合や、倍率のばらつき・変化が大きい場合は、現在の倍率を保って共通する肩・腰の位置だけを合わせます。結果には使用した場面数と、倍率を維持したかを表示します。少ない場面や体の一部からの結果は目安として重ねて確認し、手動で微調整してください。共通する部位を一度も確認できない場合は適用せず、ダイアログ内で読み直して人物を選び直せます。

部分的な映り方の検証：Chromeと実際の骨格モデルで、人物が最初の5秒だけ映る約30秒の動画から5 / 32場面を採用できました。模擬検出では一部区間の3場面、肩だけ・片側の胴体だけの1場面、倍率を維持した位置合わせ、未検出後の選び直し・中止を確認しています。いずれも見えている動画の再生位置・速度・音設定を維持し、解析用動画を終了後に解放しました。iPhone実機での検証ではありません。

処理は端末内のWorkerで行い、モデルを1回ロードして再利用します。見えているプレイヤーとは別のミュートした動画から画像を読むため、解析中も再生位置・速度・音の設定は変わりません。途中で中止でき、動画の変更や画面サイズ変更でも処理を終了します。

この操作で求めた基本の補正は1個の倍率と位置に固定し、手動の回転・遠近・背景の画角補正は維持します。手持ちのブレは次の「三脚OFF」で基本の位置に追加します。重ねる位置はパネルを閉じたり縦横を切り替えても動画の表示サイズに合わせて換算します。位置・倍率の補正値はこの画面を開いている間だけ保持します。再読み込み後は補正をやり直してください。

## 三脚OFF：手持ち動画の追従

動画を取り込むと、反転などの操作に「三脚 ON/OFF」が現れます。初期値は両方ONで、この状態では追従の骨格解析や追加の位置移動は行いません。三脚の設定は動画ごとに端末へ保存します。自分の動画・インカメの反転も初期値をOFFにしました。明示的に保存された反転設定は復元します。

1. 2本のBPMと拍の位置を合わせ、同じ姿勢の場面で基本の位置・倍率を合わせます。
2. 手持ちで撮った側を「三脚 OFF」にします。
3. 「重ねる → 位置 → 追従を解析」で2本の対象人物を確認し、「この2人で解析」を押します。
4. 解析後は通常の同期再生で位置と倍率が追従します。「追従の強さ」を0〜100%で調整でき、三脚ONに戻すと基本の位置で固定します。

片方だけOFFならON側を固定してOFF側を動かします。両方OFFなら「位置の主役」を基準に相手側を動かします。音の主役とは独立です。対応する拍の場面から肩・腰の長さ比と中心の差を測り、左右・上下移動と一様な拡大縮小だけを求めます。足の開き、手足の角度から回転や遠近を推定しません。初期姿勢への完全なフィッティングは行わず、基本の位置を決めた時点からの変化を補正します。

通常はお手本の時間で約6場面/秒を、別のミュートしたデコーダーとWorkerで事前解析します。最大1801組で、長い動画では間隔が広がります。再生中はこの結果を毎描画フレームに補間してCSSだけを更新します。追加の停止・シーク・速度変更・骨格推論は行いません。左右上下は近傍の外れ値を除いた局所回帰、倍率は中央値で平滑化し、長い未検出区間をまたいで別人の位置へつなぎません。検出が途切れた場所では追加補正を弱めます。上限は基本位置に対して画面の±20%、倍率は約0.74〜1.35倍です。

追従結果は開いている画面内だけで保持します。動画、BPM、拍の位置を変更すると破棄して再解析を案内します。反転・基本の位置・画角・主役・画面サイズの変更は、保持した骨格から再計算します。解析中の動画変更・画面サイズ変更では中止します。対象は読み取り可能な動画ファイル2本（取り込んだX動画を含む）です。YouTube埋め込みとライブのインカメは、この事前解析には対応していません。視点の大きな移動、隠れた体、フォームそのものの違いを正確に分離する機能ではありません。

検証：132件の自動テストに加え、Chromeの実動画で三脚の初期値・保存復元、BPM未設定時の無効化、中止時のWorker/デコーダー解放、タイミング変更後の結果破棄、主役切替、縦横表示、既存のピンチ操作を確認しました。揺れを加えた8秒の実映像では49組を解析し、検出が有効だった場面は63%。既知の移動に対する表示上の平均誤差は約7.8pxから4.3pxへ減少しました。これは1つの合成した手持ち揺れの検証であり、すべての撮影で同じ精度を示すものではありません。別々に撮影された2本でも解析と再生を確認しています。解析中の可視プレイヤーへのシーク・停止、追従再生中の追加シーク・停止はいずれも0回でした。iPhone実機の処理時間・精度は未検証です。

実装上、同期呼び出しによるUIの停止を避けるため、推論をWorkerへ分けています。参考：[MediaPipe Pose Landmarker Webガイド](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker/web_js)。

## 今の1コマで骨格合わせ

「重ねる → 位置 → 今の1コマで合わせる」で実行します。自動補正は位置移動と縦横同じ倍率だけです。両方が立ち姿勢なら、頭から両足首の中点までの高さと足元で合わせます。

体の曲がり・片足の浮き・姿勢の違いがある場合は、見えている胴体の左右・太もも・すねの長さの比から概算します。極端な比を除いた中央値で倍率を決め、両腰の中点（腰が見えない場合は両肩の中点）で位置を合わせます。頭や足の一部が隠れていても、使える部位が残っていれば実行できます。概算したことは画面に表示します。

肩の傾き・足の開き幅から画面の回転や遠近は推定しません。手動で決めた回転・遠近と、この操作で求めた基本の補正は保持します。自動倍率は0.5〜2倍、移動は±100%に抑え、大きな差は手動調整に残します。奥行き方向の短縮や体格差は分離できないため完全一致ではありません。肩・腰や十分な長さが検出できない場合だけ、場面変更や「位置・濃さ」での手動調整を案内します。

## 背景を基準に画角を補正

各動画の「設定 → 画角」で試せます。人体の姿勢・体格に合わせて画面を変形する代わりに、背景の固定した基準を使います。

1. 動画を止め、「水平線2点」または「壁の四隅」を選びます。番号をドラッグして基準点を合わせます。矢印キーでも微調整できます。
2. 水平線では背景の線の左端・右端を指定します。足先や奥へ続く床の線は使いません。これは選んだ線を水平にする操作であり、真のカメラ回転角の推定ではありません。
3. 四隅では人物に近い、人物と平行な壁・窓・鏡などの長方形を、左上→右上→右下→左下で指定します。実物の横÷縦を入力します（横100・縦200なら0.5）。実物が正方形のときだけ「正方形」を選びます。人体や床の四角には合わせません。
4. 「補正を試す」で元映像と比較し、必要なら強さを弱めます。「採用して保存」で練習画面にも反映されます。各動画で個別に設定でき、端末に保存します。
5. 採用・解除時は古い補正との二重適用を避けるため、重ねる位置・倍率・回転・手動遠近をリセットします。画角補正後に見比べたい姿勢で位置を合わせ直してください。

人物の奥行き、隠れた手足、広角レンズの曲がり、撮影中のカメラ移動は補正できません。動画ファイル向けで、YouTube・インカメは未対応。元のファイルやBPMは変えません。通常映像・切り抜き映像・骨格表示に同じ行列を適用します。[調査と合成実験の結果](docs/camera-correction-research.md)に方法の比較・数値・出典をまとめています。

## 背景を切り抜く

各動画の「設定 → 表示 → 背景」で、次の方式を選べます。比較・設定画面では緑背景または透明の市松模様で輪郭を確認でき、「重ねる」画面では背景を透明にしてお手本を透かします。位置合わせで調整中の相手側は「重ねる → 位置 → 背景」からも変更できます。

- **人物を自動で切り抜く**：普通の動画やインカメから、MediaPipe Selfie Segmenterで人物の領域を推定します。「輪郭の絞り込み」を上げると、確かな人物の領域だけを残します。遠くの全身、速い動き、髪や指、サイリウムは欠けたり背景が残ったりする場合があります。
- **撮影した緑背景を消す**：グリーンバックで撮影済みの映像の緑を透明にします。「緑を消す強さ」で調整します。緑の衣服やサイリウムも消えるため、撮影時の色に注意してください。

元の動画ファイルは変更せず、切り抜き表示に同じ反転・位置・倍率・遠近設定を適用します。音声とBPM同期は元の動画プレイヤーを使います。表示の画像処理はWorker内で行い、長辺640px・最大約30fps、処理待ちは1フレームまでに制限します。切り抜き画像の取得時刻も確認し、遅れが80ms＋元映像の1コマ相当（40ms）を超えた場合は元の映像に戻します。音声の時計が合っていても古い切り抜き映像だけが残ることを防ぎます。停止中の同じコマは保持し、背景をOFF→ONにすると再試行できます。

モデルはこのサイトから取得し、動画の画像を外部に送りません。Worker / OffscreenCanvas / ImageBitmapに対応するブラウザが必要です。処理失敗時は元の映像を表示します。YouTube埋め込みの切り抜き、切り抜き済み動画の書き出しは未対応です。「録画を保存」は背景処理前のカメラ映像です。背景の方式・強さ・確認用の色は、この端末に動画ごとに保存します。

## 各利用者の保存

- 動画のコピーとURL履歴は、その端末・ブラウザのIndexedDBに保存します。Cookieに動画を入れる方式ではありません。BPM・開始位置・反転設定は端末のlocalStorageに保存します。
- 動画をGitHubや運営者のサーバーへアップロードしません。各利用者のブラウザ内の履歴は、別の利用者の端末には共有されません。同じ端末・ブラウザを共用する人には同じ履歴が見えます。
- 別端末への同期、ログインアカウントごとのクラウド保存はありません。元の公開サイトとGitHub Pagesは別の保存領域なので、移行時は動画を一度選び直してください。
- 動画・URLを合わせて最近10件を保存します。使い直した項目は先頭へ移動し、11件目から古いアプリ内のコピーを入れ替えます。動画は合計1GB、1本500MBまで。容量制限や保存失敗では既存の履歴を保ち、今回だけの再生に使います。
- 「履歴に残す」のOFF、個別削除、全履歴の削除ができます。削除対象はアプリ内のコピーで、写真アプリ等の元動画は消しません。
- ブラウザのデータ削除、プライベートブラウズ、空き容量不足などで履歴が消える場合があります。原本は写真アプリ等にも残してください。「保存領域を保護」はブラウザへの保護リクエストであり、永久保存の保証ではありません。

## 外部サービスとの通信

YouTubeは公式の埋め込みプレイヤーを使います。リンクを読み込んだ際にYouTubeへ通信します。動画データの取得・ダウンロード・音声抽出は行いません。YouTubeも「重ねる」で自分の動画・インカメと半透明に重ねて表示できます。「位置」で主役を選び、相手側の濃さ・倍率・上下左右・傾き・遠近を手動調整します。背景切り抜きはこの重ね表示では使わず、動画の読み直しや再生中の自動再同期も追加しません。「YouTubeを操作」で自分の映像だけを一時的に隠し、埋め込み内の操作後に「重ね表示に戻る」で戻せます。YouTubeの反転・骨格解析は未対応です。広告、通信、頭出しの精度による同期のずれが生じる場合があります。

Twitter/Xの公開投稿は [FxEmbed API](https://docs.fxembed.com/api/twitter/operations/2statusid/) で動画情報を取得し、Xの配信元（video.twimg.com）のMP4をブラウザに読み込みます。投稿IDと接続元IPは取得サービスに伝わります。Cookie・認証情報・自分の動画は送りません。Xと無関係な外部サービスのため、停止やX側の変更で使えなくなる場合があります。非公開・削除済み・動画なし・配信形式が非対応の投稿は読み込めず、元の動画を維持してエラーを表示します。複数メディアの投稿では `/video/2` などの番号に対応し、番号なしは最初の動画を選びます。MP4は最大100MB・読込45秒まで、H.264の約720p相当を優先します。中止・動画変更・ページ終了時には取得を取り消します。

読み込み後は通常の動画ファイルと同じ同期・倍率・反転・拍合わせ・重ね表示・端末内の解析経路を使います。履歴には元投稿URLだけを残し、再読込時に再取得します。BPM・拍位置・反転は投稿IDとメディア番号にひも付けて保存します。元投稿へのリンクを動画ヘッダーに表示します。

曲名でのBPM検索はブラウザからDeezerの公開カタログへ直接問い合わせます。Apple Musicの曲リンクはiTunes lookupで曲名を取得してから検索します。検索した曲名や曲IDは各サービスへ送られます。音源・動画ファイルは送りません。BPMが未収録の場合は推測値で埋めません。サブスク音源の抽出や同期再生には対応しません。外部サービスが利用できない場合は、音源解析・手入力・TAP・rekordbox XMLを利用できます。

音声解析・動画の軽量化・骨格推定は端末内で行います。骨格モデルはこのサイトから初回読み込みます。補正は平面近似であり、3Dの体や隠れた手足を復元するものではありません。フォーム差は画角補正後、重ねる位置・倍率・手動遠近を適用する前の2D角度差で、残る撮影角度の影響を含みます。

## 音の基準と拍音プレビュー

2本のトラック上部の「曲」で「お手本／自分」を選び、右端のドロップダウンで0.25〜2.5倍を0.25刻みで変更します。細かな倍率は、下部の「速度・音」の数値入力・スライダーで調整できます。選んだ曲のBPMを基準に、もう片方の速度を合わせます。例：お手本150 BPM・自分120 BPMなら、自分の音を選び練習速度1倍にすると、お手本0.8倍・自分1倍になります。YouTubeでも主役に「自分」を選ぶと練習速度1倍を優先し、YouTube側の倍率を再生開始時に確認します。必要な倍率が通れば自分の音を1倍に保ち、丸められる場合は0.05刻みの最も近い倍率を試します。それも使えない場合は公開された速度候補から最も近い組み合わせを自動選択します。確認したYouTubeの倍率に合わせて自分側も調整し、頭出しは開始時の1回です。再生中の定期的な速度変更や再同期は行いません。インカメは音声を取得しません。

各動画の「設定 → 拍・BPM／拍の位置」の「拍音で確認」は、最初の「1」の2拍前（動画の範囲内）からその動画だけを等速・音声付きで再生します。白線が設定した拍、赤線が再生位置です。白線のタイミングでクリックを鳴らし、8拍カウントの「1」「5」は同じ高い音にします。停止・移動・終了で予約した拍音を取り消します。確認中の結果は「保存して戻る」を押すまで永続保存しません。

通常の再生中はBPMの比率で決めた倍率を固定し、時計の差を追って停止・シーク・速度変更を繰り返しません。読み込み待ちイベントが発生し、180ms後も読み込み待ちや75ms超の時計差が残る場合は両方を停止します。「同期再生」を押すと拍を合わせて再開します。曲に対する拍の設定がずれている場合は、矢印、「1拍目」、またはトラックの白い拍線で手動修正します。

軽量化では音声をAACで保持し、変換時に先頭時刻を自動で詰めない設定にしました。音声が失われた場合や開始位置・長さがずれた場合は適用せず元動画を保ちます。元々無音の動画やカメラ録画に音声を追加するものではありません。

## 動画ファイル同士の再生開始

利用者が再生を押したときに、両方を無音で準備し、指定位置のコマが読めるまで待ってから、選択中の音声を有効にして再生します。play()の完了直後に音声出力の準備で時計が遅れる場合があるため、250ms以上かつ両方の時計が80ms相当以上進むまで開始を確認します。25ms超の差があれば、進んでいる動画を一度だけ待たせて追いついたら再開します。追加のシークで新たなデコード遅延を作らず、通常再生中にはこの処理を繰り返しません。準備中は「開始を中止」でキャンセルできます。

トラックのドラッグと矢印の微調整は、両方を停止して拍だけを変更・保存します。次の同期再生・シークでは保存された拍の位置を使います。ファイル比較の倍率変更と区間ループの先頭では一度ずつ開始を準備し直します。インカメ練習は倍率変更で中断しません。自分の動画が始まる前の区間から再生した場合は、その開始位置に達した時点で自分の動画を一度だけ開始し、開始遅延も一度だけ補正します。どちらかの動画が終わると両方を停止します。インカメとYouTube埋め込みはファイル2本用の「1拍目」画面の対象外です。YouTubeは既存の各動画設定で拍を合わせますが、デコード完了を直接確認できずフレーム単位の精度には制約があります。

BPM・拍の設定画面から戻ったときは、選択中の曲を基準に相手側の停止位置を合わせ直します。拍の変更は画面更新を待たずに保存・再生処理へ渡し、入力欄から直接「保存して戻る」を押す場合も直前の値を保存します。値を編集せず設定画面を開閉しただけで、小数点以下の微調整を丸め直すことはありません。

開始遅延の回帰検証：修正前に0.5秒の開始差を再現するテストが失敗することを確認しました。修正後はChromeの実動画に0.5秒の開始待ちを注入し、両方の曲の選択で、開始後の時計差が0.08秒以内に収まることを確認。先にお手本が流れ、自分の動画が途中から始まるケースも0.1秒以内でした。その後の表示切替や再生中に補正が繰り返されないことも確認しました。この数値はPCのテスト結果で、iPhoneの描画・音声出力の遅延やフレーム単位の一致を保証する値ではありません。

読み込み遅延の模擬テストに加え、Chromeの実動画再生で、時計の差と連続する読み込み待ちイベントを与えても自動のpause・play・currentTime変更が発生しないこと、手動で指定した2点の保存と開始位置を確認しています。iPhone実機の画面・音声出力の遅延を計測した値ではありません。

YouTubeの重ね表示は、Chromeで実際の埋め込み動画とローカル動画の同時再生、比較／重ねる切替、YouTube操作用の一時非表示、手動の濃さ・位置・倍率変更を確認しています。390×844・844×390・375×667・667×375で2つの表示領域の一致とページ全体のはみ出しがないことも確認しました。模擬プレイヤーでは切替時のプレイヤー再生成・pause・play・seek要求が増えないことを検証しています。iPhone実機の確認ではありません。
