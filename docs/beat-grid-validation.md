# 音声からのBPM・拍グリッド：実装と検証

2026-09-11。提供された2本のMP4をローカルのChromeへ読み込んで比較した。動画・音声・個人の解析履歴はリポジトリや外部サービスへ送っていない。

## 採用した構成

1. ブラウザで音声を22,050 Hzにデコードし、ステレオを平均してモノラル化。
2. [Beat This!](https://github.com/CPJKU/beat_this) small0をONNX Runtime WebのWASMで実行。画面とは別のWorkerを使い、1区間ずつ推論する。GitHub Pagesで使えるよう単一スレッドとし、WebGPUや共有メモリは必須にしない。
3. 検出した拍に外れ値除去と全体の直線フィットを行い、BPMと位相を同時に求める。BPMの表示だけ小数3桁にし、保存値は丸めない。
4. AIの検出が疎／不安定な場合だけ、FFTによる全帯域・低音の立ち上がり、周期・位相の候補探索、全体フィットを使う補助解析を実行する。最初・中央・最後に十分な実測の立ち上がりがあることを確認する。
5. 白線と拍音のプレビュー後に利用者が採用する。音楽の小節頭と踊りの「1」は一致するとは限らないため、現在の白線を「1」に指定し直せる。テンポの倍・半分もプレビューで変更できる。

変速や誤検出を一定のBPMとして無理に確定しない。現在の再生エンジンは固定BPM＋起点であり、可変テンポの区間別グリッドは未実装。再生中の繰り返しシーク・速度追従は追加していない。

同じPCのChromeで、動画の読込から結果表示まで約6秒／約7.5秒だった。初回のネットワーク速度やiPhone実機の性能を示す測定ではない。

### 比較して採用しなかった方法

- Essentia.js 0.1.3のRhythmExtractor2013を実験用フォルダで使用。1本目は約137.1〜137.7、2本目は約153.7〜153.9 BPMの出力。検出時刻を全体フィットすると約138／154 BPMとなり、採用結果と同じテンポ系列だった。Essentiaはアプリには同梱していない。
- Beat This! small0は1本目で75拍・19小節頭を検出したが、2本目は15拍・10小節頭しか検出できなかった。small1、small2、final0、final1も2本目では検出系列が安定せず、大型モデルへの置き換えだけでは解決しなかった。
- 2本目を2倍・約3.16倍・5倍に増幅、ピーク正規化・RMS正規化しても回復しなかった。自動の音量調整は採用しない。
- 補助解析で150 BPM付近を約75 BPMに折り返す条件が強すぎた。自動で半分にする範囲を高速な候補へ限定し、低いテンポ帯での倍・半分の曖昧さは確認画面で変更できるようにした。90 BPMの合成音が180 BPMになる例もある。

## 数値・操作の検証

- 同一の22,050 Hz PCMから作ったJavaScriptのlog-melと公式Pythonのlog-melを比較。最大絶対差は約0.00004以下。ONNX/WASMで得たsmall0の拍時刻配列は、2本とも公式Pythonと一致した。
- 20秒の合成150 BPM音源を、配信用にビルドしたWorker・実ONNX・実WASMで解析。GitHub Pagesと同じサブパスでモデル・実行ファイルを取得し、無音が仮の120 BPMにならないこともテストする。
- 合成音、拍の欠落・余分な検出、ノイズ、部分的な音、テンポ変化を検証。STFTの窓の開始ではなく中心を時刻として扱い、波形と拍の一律のずれを防ぐ。
- 提供された両動画で前半・中盤・後半を各4.5秒再生し、予約した拍音の時刻と1／5の高音、重複がないことを確認。確認前は保存せず、微調整後にBPMと起点を保存することを確認した。
- 別WAVからはBPMだけを保存し、動画に設定済みの7.123456秒の起点を保持した。解析中止・タブ切替でWorkerとプレビューを終了した。
- 保存した2本を「1拍目から再生」した開始後の時計差は約0.037拍だった。一方、ファイル先頭から片方を遅れて開始する既存のプリロール経路では約0.15拍（約65 ms）の差が残った。グリッドのフィット誤差と動画デコーダーの開始遅延は別であり、この変更で映像のフレーム単位の完全同期を保証しない。
- Chromeの390×700、320×568、844×390、1280×900で、結果の確認・スクロール・操作と画面全体のはみ出しを確認。iPhone実機での確認ではない。

## 配布資産

モデル、フィルターバンク、前処理条件、SHA-256、出典のリビジョンは `public/beat/config.json`。small0のONNX変換には[musetric-toolkitの変換コード](https://github.com/musetric/musetric-toolkit/tree/1eeb5baf6ce796419dfcf500ae13b3247d8b6459/scripts/onnx/beat_this)を参照した。MITの権利表示は同じディレクトリに同梱。ONNX Runtime Web 1.29.0の実行資産とライセンスはビルド時に配置する。

音声をブラウザが読み出せない場合、モデルの初回取得に失敗した場合は解析を成功扱いにしない。別音源・手動の拍タップも利用できる。YouTubeやApple Musicの保護されたストリームを抽出して解析する機能ではない。

## MOVの音声読込エラーへの対応（2026-09-11）

iPhoneのスクリーンショットにあった「音を読み出せませんでした」は、モデル実行前に動画全体を `decodeAudioData()` へ渡した際の失敗。該当の `IMG_7069.mov` 自体は未提供で、正確な音声形式・iOSのバージョン・失敗原因は未確定。前回のMP4／PC Chromeでの確認だけではこの経路を検証できていなかった。

MOV／MP4／M4Aは、既存のmediabunny 1.55.7で音声トラックを取り出す。AACなどは映像のデコードや音声の再圧縮をせず、音声だけのMP4へパケットをコピーしてからWeb Audioで読む。PCMは内部デコーダーから読み、モノラル化・22,050 Hzへの変換を行う。すべて端末内で実行し、動画や音声をサーバーへ送らない。

一時的な音声の先頭だけを0秒にし、解析用PCMを組み立てる際に**元のパケットの時刻へ戻す**。先頭の空白を保ち、負のAACの準備区間を切る。MOVに限らず、MP4の先頭の空白が成功したデコードで失われる場合にも同じ処理を使う。

[WebKitの修正履歴](https://github.com/WebKit/WebKit/commit/c3244cf76da410fe534f880686d375e1390bbbfd)には、iOS 27 betaでMP4互換ブランドを持たないM4Aが形式判定で拒否される問題が記載されている。今回の出力は `mp41` 互換ブランドを含む。これは互換性対策の根拠であり、利用者の端末がその不具合に該当すると断定するものではない。

確認したこと：

- 提供済みの2本のMP4を再エンコードせずQuickTime MOVへ変換し、Chromeで検証。音声専用WebCodecsを無効化し、MOVのWeb Audio読み込みを意図的に拒否しても解析まで通る。抽出したPCMは元のMP4を直接デコードしたPCMと一致し、比較した音の位置の差は0 ms。
- 配信用アプリで両MOVの解析・拍音プレビュー・採用・保存を確認。BPMは約137.9822／153.9337。動画全体の末尾まで扱うため、前回の音声だけの長さを使った結果とは微小な差がある。確認前は保存値を変更しない。
- 同じ提供動画から作った24-bit PCM MOVも、音声専用WebCodecsなしで読めた。比較した音の位置の差は0 ms。
- 合成12秒音声で、AACの負の開始時刻、MOVとMP4の500 msの先頭空白、16-bit PCM、ネイティブデコードが使えない場合、中止、壊れたファイル、未対応の音声形式をブラウザで回帰テストする。`tests/audio-decode-browser.mjs` を公開前のCIへ追加した。

実際のiPhoneと未提供の `IMG_7069.mov` では未検証。特殊な音声形式や複雑な編集リストを持つすべてのMOVを保証しない。処理の中止後もブラウザ内部の実行中デコードが短時間続く場合はあるが、解析・保存には進まない。

## 設定画面を閉じた後の解析履歴

波形・検出拍・解析値に加え、編集中のBPM・「1」の位置・プレビュー位置を動画の元の `source.key` ごとにIndexedDBへ保存する。設定画面の開き直し、拍タップへの切替、ページ再読み込み後に同じ動画を選ぶ場合も、再解析せず復元する。軽量版への切替でも元の動画キーを使う。復元は確認画面だけで、再生や設定の適用を自動的には行わない。

各動画について最後に完了した解析を1件保持する。別音声の場合は、その音声のファイル名・バイト列・音声由来という区別も同じ記録へ保存し、音声ファイル名を表示する。未解析の音声を選んだだけでは前回の完了結果を置き換えない。再解析を中止したり処理が失敗した場合も前回の完了結果を残す。別音声の拍位置を動画へ適用しない従来の制約は維持する。

保存は最近10動画、解析用の別音声を含め合計160MB以内。動画自体は解析履歴に複製しない。既存の履歴OFFではタブ内のみで保持し、保存領域が使えない場合もタブ内で保持してその旨を表示する。動画履歴を削除すると対応する解析履歴も削除し、全履歴削除では解析用に保存した音声も消す。更新前に消えた解析結果は復元できないため、最初の1回は再解析が必要。

提供動画で、未適用のBPM `137.9823251267073` と起点 `1.45935077262521` を設定の開閉・タブ切替・ページ再読み込み後まで保持し、別動画では表示しないことを確認した。別WAVについても再読込後の拍音プレビュー、BPMのみの適用、動画の起点の保持、全履歴削除を確認。合成音源を使う `tests/built-rhythm-history.mjs` をCIへ追加した。保存・容量境界での並行更新・破損データ・保存失敗・削除は `tests/rhythm-history.test.mjs` で検証する。iPhone実機での検証ではない。

BPM設定の「曲」「手入力」タブは利用者の希望により削除し、「自動解析」「手動」の2つにし、自動解析を左・初期表示にした。解析結果のBPM・拍位置の編集は残す。

## 設定の保存と「1」のフィット

「BPMと拍を使う」の個別ボタンは削除。自動解析の調整値は、画面下の「保存して戻る」でBPMと起点をまとめて反映する。別音声の場合はBPMのみ反映する。解析中、空欄や範囲外の値、信頼できる固定グリッドがない結果、保存エラーでは設定を閉じずメッセージを出す。解析しただけ・戻る操作・履歴の復元では再生設定を自動適用しない。手動タブで保存する場合は、手動で設定した値を採用する。

タブを移動しても解析編集中の値を保持し、表示タブ等からの保存でも反映する。「拍の位置」で編集した値が、古い解析ドラフトに戻されることも防ぐ。

波形の白線は解析アンカーと現在のBPMで作る拍の目安。赤い「1」はドラッグ・タップ・左右キーで移動でき、拍音はその「1」から数える。再生中の細い青線は再生位置。「フィット」は赤線に最も近い白線または隣り合う白線の中点に合わせ、動画内の候補だけ使う。アンカーは赤線を動かしても変わらず、連打してもずれない。BPMはフィット操作で変更しない。

`tests/fit-beat-origin.test.mjs` で拍/中点・負の拍番号・境界・不正値・精度を検証。配信用ブラウザテストは実際の解析を行い、赤線ドラッグ、拍/中点へのフィット、保存だけでの適用、別タブでの保存、拍位置の直接編集、空欄と保存失敗、再読込での復元、別音声のBPMのみの適用を確認する。
